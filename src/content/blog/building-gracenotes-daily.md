# Building GraceNotes Daily: A Product Manager's Field Guide to Shipping with Lovable, Claude, and AI

*By Cindy — Founder, Product Queen Inc.*

I built [GraceNotes Daily](https://www.gracenotesdaily.com), a soft Christian devotional companion, by orchestrating Lovable, Claude (both in-editor and Claude Code), Supabase, ChatGPT for asset generation, and a lot of opinionated product thinking. This is the honest, detailed how-to I wish I'd had on day one — for the founders, PMs, and indie builders who want to ship something real with AI without ending up with a fragile, insecure, soulless product.

If you're skimming, the headline: **AI is a brilliant pair-builder, but the product still has to be a product.** Taste, security, and decisions don't get outsourced. The rest does.

---

## 1. The experience I was hoping to give users

GraceNotes Daily exists because a lot of Christian apps either (a) shout at you with verse-of-the-day banners and gamified streaks, or (b) feel like a 2007 PDF devotional booklet dressed up in a web app. I wanted something closer to what Calm did for meditation: a **soft, held, reverent** daily companion that meets you where you are.

The promise to the user is small and specific:

- A **grace note** each morning — a 2–4 sentence reflection written in God's first-person voice, anchored to a real NIV verse, that doesn't feel like it was generated by a robot trying to sound spiritual.
- A **shared daily devotional** the whole community reads together, rotating through seven weekday themes (Hope, Peace, Grief & Comfort, Gratitude, Courage, Rest, Purpose).
- A **daily chat** companion that listens, responds gently in God's voice, and knows when to stop and route a user in crisis to a real helpline in their country.
- **Heart Notes** (private journal with an AI response), **Prayers** (with answered-prayer tracking), and a **Journey** archive that quietly makes the user's spiritual life visible to them over time.
- **Daily Rhythms** — three simple habits (devotional, daily message, journal) that auto-complete only when you actually do the thing, never on a tap.

The visual language is Calm-inspired: nature-image backgrounds, two glass surfaces, Fraunces display + Nunito body, two brand greens and a gold accent. The voice is the product. Everything else serves it.

## 2. How Lovable danced with Claude

This is the part I get asked about most. Here's the actual workflow:

- **Lovable was the cockpit.** I wrote the brief, iterated on UI, scaffolded routes, wired Supabase, and ran the build. Lovable's in-chat agent (running on Claude under the hood) is excellent at translating product intent into shipped code — components, routes, Tailwind, shadcn, edge functions, migrations.
- **Claude Code was the backend surgeon.** When the work got gnarly — schema migrations, edge functions, prompt tuning, dependency conflicts, security hardening — I'd hand off to Claude Code in a terminal with a clear handover document (`CLAUDE.md`, more on this in §11). It can read the whole repo, run TypeScript checks, and make multi-file changes with more patience than chat-based agents.
- **ChatGPT generated assets.** Lovable's image tools are good for app imagery, but for one-off branded assets (the gold medallion for the streak badge, certain SVG icon sets) I used ChatGPT/DALL·E, downloaded the file, and uploaded it as a project asset. Faster and gave me more control.
- **The handoff doc was the glue.** `CLAUDE.md` is a single living document at the repo root that tracks: what's shipped, what's pending, locked decisions, the canonical prompts, server-runtime gotchas, and a dated changelog. Every code change updates it before push. Without that, picking up between sessions (or between Lovable and Claude Code) bled hours.

**The dance only works if you treat the AIs as collaborators with different strengths**, not as one interchangeable "AI." Lovable for live preview and product iteration; Claude Code for deep code work; ChatGPT for assets and second-opinion reasoning.

## 3. Mistakes I made that I would not make again

In rough order of how much they cost me:

### 3.1 The two-Supabase-projects nightmare

Early on, I had Lovable Cloud (which is Supabase under the hood) **and** a separate Supabase project I'd started before connecting Cloud. Migrations ran against one, the app pointed at the other, edge functions deployed to a third reality. I spent days debugging "missing table" errors against code that was perfectly correct — it was just talking to the wrong database.

**Never again rule:** Decide on ONE backend before you write a single migration. If you're using Lovable Cloud, use only Lovable Cloud. Do not create a Supabase project on the side "just in case." If you're using your own Supabase, do not turn on Lovable Cloud. Pick one. Migrations and `.env` values must point at the same project. Verify with a single round-trip query before you build anything that depends on it.

### 3.2 Letting the AI write Scripture

For weeks, my grace notes and devotionals were Claude writing the verse text from memory. This is wrong for two reasons: (1) Bible translations are copyrighted (NIV is Biblica's) — generating verse text at scale is a licensing risk; (2) models hallucinate verse text and references in subtle ways that a non-theology-trained eye misses.

**Never again rule:** When content has a source of truth (Scripture, legal text, medical info, anything regulated), **ground it from a database table**, never let the model write it. The model writes the reflection around the verse; the verse comes from a curated, verified table with attribution. I now have 123 verified NIV verses in a `verses` table with a 60-day rotation function.

### 3.3 Skipping the canonical-prompt rule

I had the grace-note prompt in two places — the on-demand server function and the overnight cron edge function — because edge functions can't import from `src/`. I'd update one and forget the other. Users got drift between morning and on-demand notes.

**Never again rule:** When the same prompt has to live in two files, write a comment header in both saying "if you change this, change the other" and reference it in the project's handover doc. Even better: write a script that lints for drift.

### 3.4 Not enforcing the "no em-dash" rule in code

I told the prompt "don't use em-dashes." The model complied 95% of the time. The other 5% shipped to users and broke the voice. The fix was a one-line `stripEmDashes()` sanitizer applied to every AI output before it touches the UI.

**Never again rule:** If a style rule matters, enforce it in code, not just in the prompt. Prompts are guidance; code is law.

### 3.5 Burning credits on speculative refactors

Early on, I'd ask Lovable to "reimagine" sections without a tight brief. Beautiful work, expensive work, often discarded work. Later I learned to (a) ask for a *plan* first, (b) approve the plan, (c) ask for the implementation. Or even better: ask for two or three rendered prototype directions and pick one. Plan-first saves credits and prevents regressions to locked design tokens.

### 3.6 Not writing the imagery and tone policy down on day one

I wrote the imagery policy (no alcohol, no other-faith symbols used decoratively, no AI-generated identifiable people) after I'd already had to reject several rounds of generated images. The same is true for the voice policy (God speaks in first person, never performative "I see you," no rule-of-three structures, no em-dashes). **Write the rules before you generate.** Put them in `CLAUDE.md` and reference them in every relevant prompt.

### 3.7 Action-gated habits I almost let become tap-gated

There was a moment of laziness where I considered letting the habit circle mark complete on tap. Two days later, the streak meant nothing. I reverted: a habit only completes when you do the thing — receive the devotional, send a chat message, submit a heart note. That single rule is half of what makes the product feel honest.

## 4. Moments key product decisions showed up that I could not outsource to AI

AI is great at execution. It is mediocre at taste and bad at conviction. These were the moments I had to be the human:

- **Cutting onboarding from 5 steps to 2.** The AI happily built whatever I asked. It was on me to look at the funnel and say: nobody is going to answer five questions to read a devotional. Name and faith phase only. Everything else gets inferred from chat over time, or lives in Settings.
- **Killing the translation picker.** Five Bible translations sounds like a feature. It was decorative — generation only ever used NIV. I removed the picker, standardized on NIV, added the attribution notice. One translation, done well, beats five done shallowly.
- **The streak rule.** Originally consecutive days. Then I realized: this is a devotional app, not Duolingo. Punishing a missed day is anti-pastoral. Now we count total days a user has shown up, even with gaps. That decision came from sitting with what the product *means*, not what's technically tidier.
- **"Remember When" carousel.** Resurfacing answered prayers as a soft, daily-randomized horizontal carousel — hidden until you have at least three answered. That came from imagining a specific user 90 days in, not from a feature request.
- **No "free" language anywhere.** The AI kept reaching for "free trial" / "free guide" / "sign up free." I stripped every instance. The product is dignified; the copy has to match. AI defaults to SaaS marketing tropes; you have to override them.
- **Magic-link-only auth with no password.** A faith audience skews older, less technical, often on Gmail's in-app browser. Password forms are friction and a support burden. Magic link is one tap. That's a product call, not a technical one.

The pattern: every time I let the AI default win, I shipped something more generic. Every time I held the line, the product got more *itself*.

## 5. The two-Supabase nightmare (and how to make sure it never happens to you)

Worth its own section because it cost me the most.

**What happened:** I started with a personal Supabase project. Then I enabled Lovable Cloud, which provisioned its own. The Lovable-generated `client.ts` pointed at Cloud. My migrations were running against the old one. Edge functions were deployed somewhere else again. Everything compiled. Nothing worked. The error messages — "relation does not exist" — were perfectly accurate and entirely unhelpful.

**The prevention checklist:**

1. **Pick one backend before you write any data code.** Lovable Cloud or your own Supabase. Not both.
2. **Inspect `.env` and `src/integrations/supabase/client.ts` together.** They must reference the same project ref. The project ref is the subdomain of your Supabase URL.
3. **Run one round-trip query (e.g., `select 1`) and watch it land in the right project's logs** before you build anything.
4. **Edge functions deploy to the same project as your database.** If you're using Supabase CLI, `supabase link` to the right ref. If using Lovable, deploy through Lovable.
5. **Never hand-create a "second Supabase project for testing."** Use the Supabase branching feature or RLS-isolated test users instead.
6. **In the handover doc, write down the one Supabase project ref.** When future-you or another agent picks it up, they need exactly one answer to "where does this data live?"

## 6. Where Lovable shined and where I had to step in

### Lovable shined at:

- **First-pass UI from a clear brief.** Routes, layouts, shadcn components, Tailwind tokens, responsive grids — Lovable produces beautiful first drafts faster than any human team I've worked with.
- **Iterative polish loops.** "Make the cards smaller on mobile," "add more padding between the title and subtitle," "the info icon glitches on tap — switch to popover." Lovable handles this kind of feedback gracefully and reliably.
- **Supabase wiring.** Migrations, RLS policies, GRANTs, edge function deploys — once you're in Cloud, the friction is genuinely low.
- **SEO scaffolding.** Per-route `head()` metadata, sitemap, robots.txt, JSON-LD structured data, OG and Twitter cards. Lovable's SEO review tool surfaces gaps and the agent fixes them.
- **Cross-session memory.** The project memory + chat history means the agent remembers your design system, voice rules, and locked decisions.

### I had to step in for:

- **The medallion / streak badge.** I generated the gold medallion in ChatGPT, downloaded the PNG, and uploaded it as a project asset. Faster than describing it round after round.
- **The six homepage preview SVGs.** Same — generated externally, uploaded as assets, swapped the imports. (And had to re-do it once because the first batch wasn't the updated versions I'd shared.)
- **The voice policy.** The AI writes competent devotional content. It does not, by default, write *this* product's voice. I had to write and enforce the voice rules in the prompts, in the sanitizer, and in code review.
- **Naming the streak rule, the badge tiers, the personalization contract.** These are product decisions that look like technical decisions. The AI will pick a default; you have to override with intent.
- **Imagery curation.** Every background image in `nature-background.tsx` was vetted by hand against the imagery policy. AI suggested several that violated it.
- **Catching the AI when it confidently broke things.** The model occasionally hallucinated old dates into the devotional from its training data. I had to force-overwrite the date server-side. Trust, but verify with code.

## 7. Questions I asked myself when thinking about SEO

GraceNotes Daily has a real SEO play because devotional content is searched daily and the daily devotional is shareable.

The questions, in order:

1. **What is the single page someone could land on and immediately understand the product?** → The homepage, plus the public `/devotional` page. Both get full `head()` metadata, OG tags, canonical URLs.
2. **What would a friend share?** → A devotional from a specific day. So `/devotional/$date` exists as a public, indexable, shareable archive. Each day becomes one more indexed page. That's the flywheel.
3. **What does Google need to understand this is a real product, not a thin AI wrapper?** → A proper sitemap, structured data (Article, Breadcrumb, Organization, WebSite JSON-LD), real content guides (Christian Journaling, Prayer Journaling, Daily Devotional explainers), and an `llms.txt` describing the app for AI crawlers.
4. **What keywords actually convert?** → Long-tail intent like "Christian journaling app," "daily devotional app," "answered prayer tracker." Each got its own landing route with unique title, description, OG metadata, and a soft signup CTA.
5. **Where do canonical and og:url need to point?** → At the page itself. Pointing them at the homepage (which I almost did) tells crawlers to attribute every page's metadata to "/", which silently breaks per-page sharing.
6. **What happens when a share preview is wrong?** → Crawlers cache. You have to use the platform's link preview debugger (Facebook, LinkedIn, X) to force a refresh after changing OG metadata.
7. **Should the app shell pages be indexed?** → No. `/home`, `/heart-notes`, `/journey`, `/prayers` are authenticated and useless to crawlers. The public surface is the landing pages, the devotional archive, and the content guides.

## 8. What I'm ultimately hoping this becomes

GraceNotes Daily is not trying to be the biggest Christian app. It's trying to be the one a specific kind of believer — someone who finds most Christian media too loud, too commercial, or too theatrical — quietly opens every morning and feels held by.

The longer arc:

- **Phase 1 (now):** Web app, magic-link auth, daily grace note + shared devotional + chat + journal + prayers, free to use.
- **Phase 2:** Push notifications, native iOS/Android via Capacitor (the config stub is already in the repo), a "Between Sundays" podcast feed integrated into the Listen feature.
- **Phase 3:** A small, sustainable subscription for premium audio (curated worship and meditation tracks), guided seasons (Advent, Lent, grief), and the ability to share private devotionals to a friend via a tokenized URL.
- **Phase 4:** A community surface — not a social feed, never that — but something like shared prayer walls and answered-prayer testimonies, opt-in and tightly moderated.

The North Star metric is not DAU. It's **how many users open the app on day 90.** If the product is good, that number is high. If the product is performative, that number collapses.

## 9. Critical decisions when the content is primarily AI-generated

This is where most AI products fail. They generate something that's technically correct and emotionally hollow. Here's how I tried to avoid that:

### 9.1 Ground the model wherever there's a source of truth

The verse comes from the `verses` table. The crisis hotline comes from the `crisis_lines` table, looked up by the user's country code. The weekday theme is fixed in code. The model only writes the *reflection* — the soft, contextual layer around hard, verified facts.

### 9.2 Voice rules in the prompt AND in code

The grace-note prompt has explicit rules: write in God's first-person voice, no performative "I see you," no rule-of-three structures, no em-dashes, no predictions, no naming the user's season back to them. Then the output passes through `stripEmDashes()` because the model occasionally breaks the rule.

### 9.3 Two models, picked for the job

- **Claude Sonnet** for the overnight cron grace-note generation (one call per user per day, quality matters most).
- **Claude Haiku** for the on-demand fallback, daily chat, and devotional (speed matters, cost matters, and the voice is already constrained by the prompt).
- **OpenAI GPT-4o-mini** for the daily chat companion (different model gives a slightly different conversational rhythm — that's intentional).

### 9.4 Anti-repetition is structural, not prompted

The grace-note generator pulls the last 14 days of verse references for that user and bans them in the prompt. Temperature is raised to 0.9 for variety. The verse rotation function enforces a 60-day no-repeat at the DB level. Three layers of defense against the model getting stuck on Lamentations 3:22.

### 9.5 Date and identity are server-truth, never model output

The model hallucinated dates from its training data. I force-overwrite the date server-side after generation. The user's name is never injected into the devotional body (the model started writing third-person about the user by name — "Tatiana stands at…" — which was creepy). Identity stays in the chrome, not in the AI content.

### 9.6 Safety system runs before the model

The chat-reply edge function has three tiers, in order:
1. **Keyword detection** for suicide and self-harm phrases. Hits this → look up country-specific helpline, log the flag, close the session, return the helpline reply. The main model never runs.
2. **Safety classifier** (small Claude call) returning SAFE / MILD / HARMFUL. HARMFUL closes the session. MILD lets the reply through with a gentle-redirect instruction.
3. **Streaming reply** from the main model.

You do not put the safety check after the generative call. You put it before.

## 10. Security checks when building with AI so user data stays protected

This is non-negotiable. Here's the actual checklist I worked through:

1. **Row Level Security on every user-content table.** `user_id = auth.uid()` for select, insert, update, delete. Without RLS, any authenticated user can read everyone else's data. Lovable Cloud does not enable RLS by default — you have to write the policies.
2. **GRANTs explicitly on every public-schema table.** PostgREST does not grant default privileges. Without `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO authenticated;`, RLS isn't even reached — the request errors at the permissions layer.
3. **Roles in a separate `user_roles` table with a `has_role()` security-definer function.** Never store roles on the profile table. That's a privilege escalation waiting to happen.
4. **Service role key stays server-side, always.** Never exposed via `VITE_*`, never in client code, never logged. In Lovable Cloud, the service role key isn't even accessible to the user — by design.
5. **JWT validated server-side in every edge function.** `user_id` derived from claims, never trusted from the request body.
6. **Prompt injection defenses on conversation history.** The chat-reply function sanitizes conversation history and whitelists roles before feeding the history back to the model. Without this, a user can paste "ignore previous instructions" and break the safety system.
7. **Webhook signatures verified before processing.** Every public API endpoint that mutates data verifies an HMAC signature with a timing-safe comparison.
8. **Magic-link auth, no passwords stored.** Smaller attack surface. Supabase handles the email/token lifecycle.
9. **Email PII hardening migration.** Email addresses on the profiles table are protected by an RLS policy that only lets the owner read their own.
10. **No secrets in `.env` checked into git.** Only the publishable (anon) key. Everything else lives in Supabase secrets and Lovable environment variables.
11. **Regular dependency scans.** Patched `ws`, `undici`, `js-yaml` transitive vulnerabilities using `package.json` overrides after a security scan flagged them.
12. **Imagery and content policies enforced in code review, not just in prompts.** AI will generate something inappropriate eventually. Catch it before it ships.
13. **Run the security scanner before publishing.** Lovable has one built in. Read the findings. Fix the critical ones. Don't publish over an open critical finding.
14. **Re-verify safety data (crisis hotlines) every 6 months.** Numbers change. A wrong helpline number is worse than no helpline number.

## 11. The CLAUDE.md rule (and why it saved me)

`CLAUDE.md` is a markdown file at the repo root. It contains:

- TL;DR of where the project is today
- What's shipped vs. pending vs. not started
- Locked design and product decisions (the "do not touch" list)
- The canonical prompts and where they live
- Server runtime gotchas (what works on Cloudflare Workers, what doesn't)
- A dated changelog of every meaningful change

**The rule:** every code change updates `CLAUDE.md` before push. No exceptions.

Why it matters: every new AI session — whether Lovable, Claude Code, or a human collaborator — reads it first. It collapses what would be an hour of "figuring out the codebase" into five minutes of context. It prevents the AI from re-litigating locked decisions. It tells you, six weeks later, why you made a weird-looking choice.

If you take one thing from this whole essay, take this: **write a CLAUDE.md from day one.**

## 13. What I'd tell another builder about doing this more efficiently

If I were starting GraceNotes Daily again tomorrow, knowing what I know about how Lovable and Claude actually behave:

1. **Write `CLAUDE.md` and the locked-decisions list before the first feature.** Voice, imagery, design tokens, auth method, backend choice. Five minutes upfront saves five hours of reverting.
2. **Pick ONE backend.** Lovable Cloud, or your own Supabase. Never both. Verify the project ref matches across `.env`, `client.ts`, and your migrations.
3. **Ask Lovable for a plan before any large change.** "Plan first, then implement after I approve." This single habit cuts credit burn and prevents regressions.
4. **Use rendered prototype options for design exploration.** Lovable can generate 2–3 visual directions for you to pick. Pick once, then build. Don't iterate from scratch.
5. **Hand off to Claude Code for backend surgery.** Migrations, edge functions, dependency conflicts, security hardening, prompt tuning across multiple files. Lovable can do it; Claude Code does it with more patience and a wider view.
6. **Ground every AI output that has a source of truth.** Verses, legal text, medical info, dates, identity. Model writes the reflection. Database holds the facts.
7. **Enforce style rules in code, not just prompts.** Sanitizers are a one-line investment with a forever payoff.
8. **Run the security scanner before every publish.** Read the findings. Don't ship over a critical.
9. **Cap the prompt drift problem early.** If a prompt lives in two files, comment it loudly and reference it in `CLAUDE.md`.
10. **Use ChatGPT for one-off branded assets.** Faster than 12 rounds of "make the medallion more gold."
11. **Treat AI defaults as suggestions to override.** "Free trial," generic SaaS gradients, performative empathy, inappropriate imagery, three-part rhetorical structures. The AI will reach for them; you have to reach back.
12. **Write the changelog as you go.** Dated entries in `CLAUDE.md`. Future-you, and every future AI session, will thank you.
